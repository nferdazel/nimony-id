# Errors as Values

## What this chapter is for

Chapter 8 gave you routines that always return what their signature promises. This chapter is about the
routine that cannot: the one whose caller has to be told that the work did not happen. Nimony has exactly two
ways to say that, an enum value and a `ref` object, and the plain one carries no data at all. Learning where
the payload went is most of this chapter.

The shape the language is built around is: a routine **returns** an `ErrorCode` when failure is ordinary and
the caller is expected to decide, and **raises** an `ErrorCode` when failure has to interrupt a whole call
chain. Both are the same enum. What Nimony does not have is Nim 2's exception object, so `except` has no
`.msg` to read and no stack trace to unpack.

## Failure that the caller checks

`ErrorCode` is an ordinary enum, declared in `lib/std/errorcodes/errorcodes.nim:4` in a file generated by
`tools/gen_errorcodes.nim`. It has 63 members at this pin, from `Success` at ordinal `0` through
`OverflowError`, `Failure`, `BugError`, `IndexError`, `SyntaxError`, `IOError`, `KeyError`, `ValueError` and
the rest, ending in nine `Reserved` slots kept for later. `sizeof(ErrorCode)` is 1.

Because it is an enum and nothing else, a routine can simply return it:

```nim
proc classify(ch: char): ErrorCode =
  if ch < '0' or ch > '9': return SyntaxError
  Success
```

The caller compares:

```nim
let code = classify('x')
if code == Success:
  echo "fine"
else:
  echo "rejected with ", code
```

Three details are worth knowing before the raising half.

`Success` is ordinal `0` but it is not a `bool`. `if code:` is refused with ``Error: expected `bool` but got: ErrorCode``, so the comparison is the only way to test it — which is good, because `== Success` says what it means.

`$` is defined for the enum, so `echo code` prints the member name (`SyntaxError`), and `ord code` gives the
number. That name is the whole diagnostic. There is no message string attached to a code, nothing to append
context to, and no place to put a source position.

And a returned code cannot be dropped by accident: a bare call in statement position is refused with
``Error: expression of type `ErrorCode` must be discarded``. If deliberate ignoring is what you want, mark the
routine `{.discardable.}`; otherwise the compiler has just forced you to decide, which is the point of
returning a code at all.

## Failure that interrupts

Returning a code only works while every caller remembers to check it. The moment a failure has to travel up
through routines that cannot do anything useful about it, the language needs the other mechanism, and it is a
`raise`:

```nim
proc digitValue(ch: char): int {.raises.} =
  if ch < '0' or ch > '9': raise SyntaxError
  result = ord(ch) - ord('0')
```

The pragma is not decoration. Nimony's default for a routine is *non-raising*, the opposite of Nim 2
(`doc/porting.md:100-113`), and the compiler enforces it in both directions:

- `raise` in a routine without the pragma is refused, ``Error: `raise` only allowed within a routine with `raises` pragma`` (`src/nimony/sem.nim:3736`). A `raise` outside any routine is refused with a shorter message, ``Error: `raise` only allowed within a routine`` (`src/nimony/sem.nim:3733`); there is no raising at module top level.
- Calling a `{.raises.}` routine without a `try` is refused, ``Error: cannot call a routine marked as `.raises` outside of a `try`..`except` block`` (`src/nimony/derefs.nim:674`).

The second rule surprises people in one specific case: it is about the signature, not the body. A `{.raises.}`
routine that cannot possibly fail still has to be called inside `try`, because the caller compiles against the
declaration.

`{.raises.}` is shorthand for `{.raises: ErrorCode.}` (`doc/language.md:4135`), and writing it out longhand
changes nothing. `{.raises: [].}` is accepted and means what the default already means.

## Catching

```nim
try:
  echo digitValue('4')
  echo digitValue('z')
except ErrorCode as e:
  echo "caught ", e
```

`e` is the code, not an object. `e` prints `SyntaxError`, `ord e` is `7`, and `e == SyntaxError` is `true`.
What does not exist is `e.msg`: writing it is refused with ``Error: undeclared field: 'msg' for type ErrorCode``.
A reader porting Nim 2 code will reach for it out of habit; the fix is that the information was never stored,
so it has to be built at the throw site or at the catch site.

The arms are type filters, tried in order (`doc/language.md:4149-4163`). Two shapes follow from that.

First, `except` matches types and not values. `except IOError:` looks reasonable and is refused with a message
that states the rule better than the manual does:

```
Error: `IOError` is an `ErrorCode` value, not a type; write `except ErrorCode as e:` and test `e == IOError`
```

The test goes inside the arm, and a `case` over an `ErrorCode` needs an `else`, because the enum has 63 members
and not all of them are interesting:

```nim
try:
  f()
except ErrorCode as e:
  case e
  of KeyError: echo "key"
  of Failure: echo "general failure"
  else: echo "other ", e
```

Second, a bare `except:` catches everything, whichever family raised, so it works as the last arm of any chain.
Arms are tried from the top, so a catch-all placed first shadows everything under it.

Bind once. One `except ErrorCode as e` arm with a `case` inside is the safe shape, and the reason is not
style. At this pin two `except ErrorCode as` arms in the same chain are unsafe: the second bound name builds
fine while its body ignores it, and stops the C backend with `[Bug] could not find symbol: e2.0`, exit 1, the
moment that body reads it — after type checking has already passed. Listing a `ref` arm anywhere in the chain
avoids it, and that has a cause rather than being luck: a ref raise reaching the frame selects a different
lowering, `emitDispatcher` (`src/nimony/derefs.nim:1316-1317`), which rewrites the whole chain into one
synthesized handler with a single binding, so the second binding never walks the path that loses it. It is still
not a shape to design around. The dispatch goes inside one arm.

### `finally` and `defer`

`finally` runs on both paths, and it runs before the error leaves the routine:

```nim
proc guarded(): int =
  try:
    result = digitValue('q')
  except ErrorCode as e:
    echo "handled ", e
    result = -1
  finally:
    echo "finally ran"
```

The output is `handled SyntaxError`, then `finally ran`, then `-1`. `defer: cleanup()` compiles to the same
outer `finally` and runs on the failing path too (`doc/language.md:4222-4248`).

A `try` that has only `finally` and no `except` does **not** satisfy the raising-call rule. The check wants a
catcher, and `finally` is not one.

### A `try` is an expression

`try` can produce a value, and the `except` arms have to agree on its type:

```nim
let n = try:
    digitValue('5')
  except ErrorCode as e:
    echo "defaulted after ", e
    -1
```

This is the usual way to give a failing call a fallback without a mutable `result` in between.

## Initialise `result` before the `try`

One trap sits in the interaction with Chapter 8's definite-assignment check. When the only assignment to
`result` is inside the `try` body, the checker cannot prove the assignment happened — the body may raise before
reaching it. The build stops with:

```
Error: cannot prove that result has been initialized
```

The fix is one line at the top of the routine:

```nim
proc readIt(path: string): string =
  result = ""
  try:
    result = readFile(path)
  except ErrorCode as e:
    result = "error: " & $e
```

`doc/porting.md:149-155` records the same caveat for ported code, and it is the single most common build break
when a Nim 2 routine is converted mechanically.

## The other family: a `ref` exception

An `ErrorCode` carries no payload. When a failure has to say *which* key was missing or *where* parsing stopped,
the raisable type is a `ref` object that inherits `Exception`:

```nim
type ParseError = ref object of Exception
  at: int

proc checkAt(s: string; i: int) {.raises: ParseError.} =
  if i >= s.len: raise ParseError(at: i)
```

`Exception` is declared at `lib/std/system.nim:712` with one field, `msg: string`, and that is where `.msg`
comes from when this family is used. The arm is a type filter again, and it accepts the raised type and its
subtypes:

```nim
try:
  checkAt("abc", 9)
except ParseError as e:
  echo "no character at ", e.at
```

The ancestor is mandatory. A plain `ref object` with no `Exception` in its chain has no runtime type
information, and both `{.raises: T.}` and `except T` refuse it: ``Error: `.raises` takes a `ref` object type
with RTTI, not `ref Bare.Obj not nil`; inherit its object from `Exception` ``. An `object of Exception` is not
enough either; the pragma wants the `ref`.

The two families never convert, in either direction, and the messages say so rather than silently
reinterpreting (`src/nimony/derefs.nim:651-684`):

```
Error: `ErrorCode` raised here cannot leave a routine that raises `ref ParseError.Obj not nil`,
and nothing converts one into the other
```

So a routine either raises codes or raises ref exceptions, and a chain that has to cross from one to the other
does it explicitly: catch the code, `raise` a constructed ref object in the `except` arm. That conversion is a
statement in your source, not a compiler behaviour.

One row of that page is wrong, and the neighbouring row is not. `doc/porting.md:106` gives the catch shape as
`except IOError:` with "no `as`, no `.msg`"; at the pin `as` is required — `except IOError:` does not compile —
and `.msg` does exist, on the `ref` family. The construction row at `:105` is the Nimony column's description of
what Nim 2 code does, and it is right about Nim 2: `newException(IOError, "text")` is what a port arrives with,
and `:121` tells you to convert it. Converted as written it does not work, because `IOError` is a value, not a
type; the call is refused with ``expected: typedesc[T] but got: ErrorCode``. `newException` is written for
`object of Exception` types (`lib/std/system.nim:717-722`); for a code, the raise *is* the value.

## The compatibility switch that swallows errors

`doc/language.md:4994` lists a `"canraise"` feature, "allows procs without a `raises` annotation to raise
exceptions". It compiles, and it is a trap worth one paragraph. With `{.feature: "canraise".}` at the top of the
module, this program builds and prints `before call`, `in f`, `after call`:

```nim
{.feature: "canraise".}

proc f() =
  echo "in f"
  raise KeyError

f()
echo "after call"
```

The raise does not reach the caller. The routine returns, the caller continues, and the error is gone — no
diagnostic, no exit code, no catch. The lowering has no error channel for a routine that does not declare one,
so the raise degrades to a return (`src/hexer/eraiser.nim:690-712`), and it is a return from that point: the
statement after the `raise` never runs either, so the routine stops early and still reports success. A
`{.raises.}` routine in the same module still works normally; it is the unannotated one that loses the failure. Do not use this feature to quiet the
compiler.

## Leaving the program

When a failure is not recoverable where it is caught, `quit` ends the program with a message and exit code 1.
The message goes to standard output, not standard error — worth knowing before you pipe a program's result.

```nim
try:
  f()
except ErrorCode as e:
  quit "fatal: " & $e
```

`src/lib/compat2.nim:17-28` wraps exactly this pattern as `onRaiseQuit(call)`, and the comment there explains
why it exists: to stop `raises` from spreading through every layer without silently swallowing the error.
Chapter 21 covers exit codes and arguments properly; for this chapter, `quit` is how a `main` turns a caught
code into a non-zero exit.

## Nim 2 delta

*What Nim 2 did.* `raise newException(IOError, "msg")` built an object on the heap, carried the message and the
stack trace, and `except IOError as e: echo e.msg` read it back. Procs raised freely unless annotated
`{.raises: [].}`.

*What Nimony does.* Codes are values: `raise IOError`, no allocation, no message, no trace. The default is
non-raising, and a routine that raises says so with `{.raises.}`. A `ref` exception still exists for readers who
need a payload, but it is a separate family, it must inherit `Exception`, and it does not convert to or from an
`ErrorCode`.

*What breaks if you keep the habit.* Three things, in the order a port hits them. `.msg` on a caught code is a
compile error. `newException(IOError, ...)` does not build. And every routine along a raising path has to be
annotated or catch, so a module that never declared `{.raises.}` will not compile at all — which is the compiler
telling you where the decisions belong.
