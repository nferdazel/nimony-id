## Questions for the Head of Engineering

**A. Is #21 a defect or intended?** Two `except ErrorCode as` arms where the second body reads its binding die
in `shoggoth` with `[Bug] could not find symbol: e2.0`, exit 1, after `nimsem` accepted the program. The trigger
is narrow: the second binding must be *read* (`mc1` builds, `mc2` does not, same file except one `echo`), and a
`ref` arm anywhere in the chain makes it disappear (`md1`, `nb01`). `ma2` shows it is not about arm count; `ma3`
shows position does not matter. If it is a defect, it wants a minimal repro in `ERRATA.md` — `mc2` is the
smallest I have. What I need is a ruling I can cite: defect candidate, or a shape the book should simply never
write (it already does not).

**B. Why does the `ref` arm in the same chain change the lowering (#23)?** `md1`/`ma2`/`nb01` all build with two
bound `ErrorCode` arms when a `ref` arm is present, and fail without one. I could not read the cause out of
`trTry` (`src/hexer/eraiser.nim:735-846`) in one pass. If the answer is "the ref arm forces a different
`exceptVar` path", that is worth one sentence in `ERRATA.md` so a later probe does not re-derive it.

**C. `canraise` (#38): is the swallowed error the intended contract of the feature, or a hole?** The feature
table says it "allows procs without a `raises` annotation to raise exceptions" (`doc/language.md:4994`). What it
does is compile the `raise` and drop it: the routine returns, the caller continues, nothing is reported and the
exit code stays 0. `trRaise`'s own comment (`src/hexer/eraiser.nim:694-698`) says a bare `raise` degrades to
`(ret .)` when there is no error channel. Two questions in one: is that degradation intended for a *bare* raise
only (which is what the comment is about), and does the feature being at pin level mean a port can rely on it?
The chapter currently calls it a trap and forbids it; if the true answer is "planned to propagate later", the
sentence changes shape.

**D. `overload`/`case`-style exhaustive dispatch aside, is `case e` on `ErrorCode` supposed to need `else`?**
#19 says yes, with all 62 remaining members named. A reader may want `of Success`/`else` only, which works, so
nothing is blocked; I am asking whether the full-enum diagnostic is the intended teaching moment or a message
worth shortening in the manual.

**E. `quit` writes to stdout (#40).** Confirmed by running the binary directly: stdout has the message, stderr is
empty, exit 1. `doc/porting.md:120-122` calls it the "catch site" idiom without saying where the message goes. Is
stdout intended (so a shell pipeline sees it as data) or is that a wart? The chapter states the fact and warns
about piping.

**F. `except` with a bare `ref` type and inheritance.** #31 has `E1` catching `E2` when `E2 = ref object of E1`
(`d04`) and *not* catching when the two are siblings (`nt01`: `E2` arm taken). Is `isRefSubtype`
(`src/nimony/derefs.nim:655-664`) the only rule, i.e. the same one Nim 2 uses? I teach "the raised type and its
subtypes" and want that sentence to be exactly right.

**G. `try` as an expression with a raising branch (#26).** It works, including with `finally` (`zt02`), but
`doc/language.md:4201-4218` shows it only with `parseInt`. Is the type rule "every `except` arm and the `try`
body must unify" the whole contract, or is `void` allowed on some arms?

### Answers A–G

**A.** A defect, not a shape to avoid: `nimsem` accepts the program and `shoggoth` dies with a `[Bug]` line, which is the compiler reporting itself. The cause is the lowering split: `derefs.trTry` passes `ErrorCode`-only arms through untouched, and hexer's `trTry` hoists only the **first** arm's `as` binding (`eraiser.nim:776`, `:786-790`), then skips every later one (`:823-824`), so `e2` is emitted as a use with no declaration and C compilation fails. `mc2` is minimal enough to file; `mc1` versus `mc2` is the trigger proof, one `echo` apart.

**B.** A `ref` arm (or any ref raise reaching the frame) selects `emitDispatcher` (`derefs.nim:1316-1317`), which rewrites the whole chain into one synthesized handler with a single binding; the separate-`except` path that loses the second binding is never emitted. It is a different lowering, not a rule about arm order or count (`ma3` has the ref arm first and still builds).

**C.** Not intended: the feature's documented job is to relax the annotation check (`doc/language.md:4994`), and `sem.nim:3734-3735` does exactly that; nothing documents that the error is then dropped, no test asserts it (the three `canraise` tests either annotate the raising procs or expect a different refusal, `traise_ref_lacks_rtti.nim:38-39`), and Nim 2 propagates the same shape. Treat as a defect candidate for silent error loss, not as a porting contract: a port cannot rely on it.

**D.** Intended: `case` over a 63-member enum needs `else` by the same exhaustiveness rule as any enum, and the full list is the check working, not a message bug. The chapter's `else` shape is correct; no ERRATA row.

**E.** Neither: `quit(msg)` is explicitly `echo msg; quit QuitFailure` (`lib/std/syncio.nim:547-550`), so stdout is the implementation, not a compiler accident. Nim 2.4.0 puts the same message on stderr, so it is a delta to state, not a defect to file; the chapter already warns about piping and only needs the contrast clause.

**F.** `isRefSubtype` is the rule, at `derefs.nim:636-646` (not `:655-664`, which is inside `raisesTypeOf`/`checkRaise`): same object key, or an ancestor in the inheritance chain; siblings do not match, which is why `nt01` takes the second arm. The prose sentence "the raised type and its subtypes" is exactly right.

**G.** Body and every `except` arm must unify, and `finally` is a statement, so it must be `void`: a value in `finally` is refused with `expression of type int64 must be discarded` (`gx1`), and a `void` arm in the expression form is refused with `got: void but wanted: int64` (`gx2`). `doc/language.md:4201-4218` states the same rule; no arm may be `void` when the `try` produces a value.

### ERRATA rulings

1. **`doc/porting.md:104-108` — documentation defect, narrowed to one row.** `:106` (Catch shape) is wrong: the Nimony column says `except IOError:` with no `as`, and at the pin that is refused with the message in claim #18; `.msg` is absent on `ErrorCode` but present on the `ref` family. `:105` (Construction) is **not** wrong: `newException(IOError, "msg")` is the Nim 2 column, and `:121` says to convert it. The row must say that; it must not call the construction row a defect.
2. **Two bound `ErrorCode` arms — defect candidate, file it.** `mc2` (8 lines) is the repro: `[Bug] could not find symbol: e2.0`, exit 1, after sem accepted it. Cause as in A/B; the two source sites are `derefs.nim:1316-1317` and `eraiser.nim:776`, `:823-824`. The book keeps "bind once" as the rule; the row records a compiler bug, not a language rule.
